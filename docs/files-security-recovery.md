# Files storage, deletion and recovery

Reviewed 16 November 2026 against `functions/_files.js`,
`functions/_fileversions.js`, `functions/_filesapp.js` and the actual local
D1/R2 security fixtures. This describes the implemented boundary, not a claim
that production backups have been inspected or a recovery drill completed.

## Privacy boundary

Files metadata lives in owner-scoped D1 rows. Object keys are generated by the
server and are never derived from a filename or supplied by a caller. The
dedicated `FILES_R2` bucket is `inflite-private-files`; deployment verifies that
its managed public domain is disabled and no custom domain is enabled. Keep
that check enabled and the bucket separate from public/native media storage.

The service receives plaintext upload bytes and can read stored content. Files
does not implement client-side encryption or an end-to-end key boundary. R2
infrastructure encryption is separate from end-to-end encryption; operator or
service compromise remains in the threat model. D1 names, sizes, MIME labels
and version metadata are also readable by the service. Chat's encryption
claims must not be applied to Files.

Every Files API uses the authenticated cookie owner, an exact canonical Today
origin and a captured-owner precondition. A native content download may omit
the captured-owner header but still resolves only that cookie owner's item.
There are no public Drive share links in these routes. Content is returned as
an attachment with `application/octet-stream`, sandbox, `nosniff`, same-origin
resource policy and private/no-store headers. A supplied MIME type is metadata,
not authority to execute content in an InFlite page.

## Deletion and retention

- Trash keeps bytes and charged quota for 30 days; permanent purge removes
  current bytes, historical revisions and replacement reservations.
- At most 20 earlier versions are retained. Replacements and restored versions
  use separate immutable objects; older versions are charged to quota.
- Account deletion closes the Drive before object cleanup. All current and
  historical read paths, mutations and upload finalization must respect that
  fence. The fence stays until the final account transaction removes the user.
- Known object cleanup must succeed before account deletion completes. Failed
  ordinary item cleanup and objects left by terminated uploads are reclaimed
  by the scheduled orphan scan. It examines only `files/`, waits until objects
  are over one day old and works through bounded pages. That grace period is
  not a guarantee of deletion exactly one day later.
- An already-open response cannot be recalled from a device. Service-side
  deletion also cannot delete a recipient's downloaded copy or automatically
  rewrite an independent backup.

## Recovery requirements and safe drill

The account export's Files section is metadata only. Neither that JSON, the
application's version history nor D1 Time Travel alone is a complete Drive
backup. Restoring metadata without matching R2 objects can produce unreadable
files; restoring bytes without metadata does not restore ownership, folders,
versions or quota. Object keys must be preserved exactly.

Before describing Drive as backed up, record the actual independent R2 backup
mechanism, D1 recovery window, retention/deletion policy, restore permissions
and agreed recovery objectives. None of those production settings was changed
or verified by this source audit.

1. Restore an authorized D1 snapshot and its matching immutable R2 object set
   into an isolated Worker, private bucket and database. Use synthetic or
   appropriately controlled data; never point the drill at production.
2. Keep cron, orphan sweeps, account deletion and all external integrations
   disabled until consistency has been checked. An orphan sweep against
   mismatched metadata can destroy the only remaining object copy.
3. Reconcile every ready node and history row to an object with the expected
   size (and independently recorded digest where the backup provides one).
   Reconcile owner associations, folder trees, historical versions, account
   fences, and `used`/`reserved`/`nodes` totals. Do not treat R2 ETags as a
   universal content hash.
4. Apply the deletion ledger and account lifecycle changes made since the
   snapshot so recovery does not resurrect deleted accounts or files. Restore
   secrets separately through the existing secret manager; never put them in
   a manifest or log.
5. Prove owner isolation, signed-out denial, exact content, version restore,
   stale-write rejection, quota limits and deletion during an active upload.
   Record evidence and timing before considering any production recovery.

Fixtures prove application behavior with real local SQLite transactions and
R2 streams. They do not prove production bucket IAM, independent backup
coverage, infrastructure encryption settings or disaster recoverability.
